# Windows build baseline (recon)

Date: 2026-10-25. Branch `windows` (= upstream main, cec8b92f1). Zig 0.17.0, Windows 11, x86_64.
All builds run with `-j4` through the test-lock. No tracked file was modified.

## 1. Summary

| Target | Result | Wall | Notes |
|---|---|---|---|
| `zig build -Demit-lib-vt -j4` (what CI runs) | PASS | 75 s cold (deps already fetched) | ghostty-vt.dll/.lib/.pdb, ghostty-vt-static.lib, headers, 2 .pc files. Peak MaxRSS 903M (translate-c exe), 883M (compile lib). |
| `zig build test-lib-vt -j4` | NOT COMPLETED | killed at ~13 min | 3712 pass, 33 skip, then stuck. Tests are extremely slow in Debug (see 3.2), not a compile failure. |

Bottom line: libghostty-vt builds on native Windows today; the full Ghostty core (`src/main_c.zig` lib, and the
`ghostty-test` unit-test exe) does not even get past C header translation, and behind that there are further
compile and link errors.

## 2. Toolchain and environment findings

- Zig: `C:\tools\zig-x86_64-windows-0.17.0\zig.exe`; `zig env` default target is `x86_64-windows...-gnu`.
- IMPORTANT, correction to the brief: Visual Studio 18 Build Tools ARE installed:
  `C:\Program Files (x86)\Microsoft Visual Studio\18\BuildTools\VC\Tools\MSVC\14.51.36231` (cl.exe, headers,
  `lib\x64\libvcruntime.lib` etc.). It is not on PATH (`where cl` fails) but Zig's `WindowsSdk.find` locates it.
  Windows SDK 10.0.26100.0 is also present (`ucrt\x64\libucrt.lib`). So the MSVC-ABI link below really uses
  MSVC libs; "nothing needs MSVC" is untrue for the default target.
- Default ABI is MSVC: `src/build/Config.zig:105-116` forces `abi = .msvc` when targeting windows with no explicit ABI
  (comment: gnu ABI objects have invalid COMDATs that MSVC link rejects, LNK1143). All logs show `native-native-msvc`.
  `-Dtarget=x86_64-windows-gnu` is accepted and works for lib-vt (CI cross matrix uses it on Linux).
- Defaults on Windows (Config.zig + backend enums): `app_runtime=none` (only `none`, `gtk` exist), `renderer=opengl`
  (only `opengl`, `metal`), `font_backend=freetype_windows` (FreeType + built-in `C:\Windows\Fonts` scanner; no DirectWrite),
  `simd=true`, `sentry=false`, `i18n=false`, `emit_terminfo=true` (Windows-specific), `emit_themes=true`, `emit_docs` only if pandoc found.
- There is no Win32 / ConPTY app runtime. `-Dapp-runtime=none` means "libghostty" (embedder-driven), not an exe;
  `config.emit_exe` is gated on `app_runtime != .none`. With `none` and not lib-vt, build.zig:210-238 builds
  `GhosttyLib` shared+static and installs `ghostty-internal.dll` / `ghostty-internal-static.lib` + header
  (this is the "libghostty" that a Windows apprt would sit on).
- Build options relevant to Windows (from `zig build --help`): `-Dtarget`, `-Doptimize`, `-Demit-lib-vt`, `-Demit-exe`,
  `-Demit-test-exe`, `-Demit-bench`, `-Demit-helpgen`, `-Demit-docs`, `-Demit-terminfo/-termcap/-themes`, `-Dfont-backend`,
  `-Drenderer`, `-Dapp-runtime`, `-Dsimd`, `-Dvt-features=`, `-Dtest-filter=`, `-Dversion-string`, `-Dstrip`.
  Steps: `install`, `run`, `test`, `test-lib-vt`, `test-lib-vt-build`, `test-lib-vt-schema` (needs python3), `dist`, `distcheck`, ...
  Zig build flags: `-j<N>`, `--maxrss`, `--summary all` (shows per-step MaxRSS), `--fetch`.
- lib-vt artifacts are always generated by build.zig (`GhosttyLibVt.initShared/initStatic`), even without `-Demit-lib-vt`;
  `-Demit-lib-vt` just changes defaults (no exe, no tests of the app, no docs, version from lib_version).
  On Windows the static lib is renamed `ghostty-vt-static.lib` to avoid clashing with the DLL import lib `ghostty-vt.lib`.

## 3. Details

### 3.1 `zig build -Demit-lib-vt -j4`: PASS
Output in `zig-out/`: `bin/ghostty-vt.dll` (9.2 MB), `bin/ghostty-vt.pdb` (12.8 MB), `lib/ghostty-vt.lib` (57 KB import lib),
`lib/ghostty-vt-static.lib` (27 MB fat archive), `include/ghostty/vt/*.h`, `share/pkgconfig/libghostty-vt{,-static}.pc`.
51/51 steps. Slowest steps: ghostty-vt-static 42 s / 883M, ghostty-vt 38 s / 863M, translate-c exe 18 s / 903M, highway 11 s.
Peak RAM stays well under 1 GB per process at -j4; fine on this machine.

### 3.2 `zig build test-lib-vt`: does not finish
- Both test exes (`terminal` vt module: 3746 tests; vt_c: 3259 shown in the other binary) compile and start.
- Zig build reported `run test 3712 pass, 33 skip, 1 crash` only after I killed the stuck exe (about 13 min, 100% CPU on both
  exes, ~48 MB RSS, not hung on a lock: running the exe directly shows steady progress).
- Direct run of the 94 MB `test.exe` (no `--listen`): ~870 tests done at 60 s, ~900 at 65 s; a block of `terminal.PageList`
  prune/grow tests ("grow prune required with a single page", "set max lines prunes immediately...") each take tens of seconds.
  Those tests pass in isolation in a few seconds (`-Dtest-filter="set max lines prunes immediately"` = 18 s wall including compile).
  So: Debug-mode slowness that is much worse than on Linux and/or order dependent (suspect page allocation/zeroing path
  on Windows, e.g. VirtualAlloc-backed pages or `memset` override cost); the final test reported when killed was
  `terminal.search.screen.test.reloadActive partial history cleanup on loop append error` (passes alone: `-Dtest-filter="reloadActive partial history cleanup"` rc 0, 44 s).
  Needs a follow-up with per-test timing; use `-Doptimize=ReleaseSafe`/`safe` to check whether it is pure Debug cost.
- CI runs this exact step on Windows with a 45 min timeout, so upstream presumably completes it on a faster runner.
- Note: `zig build` captures no per-test output; for diagnosis run the exe from `.zig-cache/o/<hash>/test.exe` directly
  (it has no filter flag; only `--listen`, `--seed`, `--cache-dir`).

### 3.3 `zig build -Dapp-runtime=none` (and `test`): FAIL at translate-c
See section 4. Same on `-Dtarget=x86_64-windows-gnu`.

## 4. Failure chain for the full core (`ghostty` module, used by libghostty and by `zig build test`)

The first error is in the real tree. Errors 2..N below were found by peeling layers in a SCRATCH COPY of the repo
(`scratchpad/gcopy`, repo itself untouched); each fix only exposes the next stage, so this list is a lower bound of the work.

| # | Stage | Location | Message | Root cause |
|---|---|---|---|---|
| 1 | translate-c `posix_c` | `src/build/SharedDeps.zig:222` (`.path = "pwd.h"`) | `posix_c.h:2:10: fatal error: 'pwd.h' not found` | POSIX header, absent on MSVC and mingw. Hits both -msvc and -gnu. |
| 2 | translate-c `posix_c` | `src/build/SharedDeps.zig:225` (`"unistd.h"`) | `posix_c.h:4:10: fatal error: 'unistd.h' not found` (after removing pwd.h) | POSIX header (errno.h, signal.h, sys/types.h are found fine on msvc). |
| 3 | Zig analysis | `src/termio/Exec.zig:2003` (also 2007) | `member function expected 2 argument(s), found 3` | Windows branch already in tree but wrote 0.16-style `args.append(alloc, x, 0)`: `dupeSentinel(...)` sentinel arg misplaced; not a platform problem, plain bug in an untested `#if windows` path. |
| 4 | Zig analysis | `src/renderer/Dmabuf.zig:44:46` | `expected type '*anyopaque', found 'comptime_int'` | `fds: [max_planes]std.posix.fd_t = @splat(-1)`: `fd_t` is `HANDLE` (pointer) on Windows. Linux dmabuf code is reached via `renderer.OpenGL.ExportedFrame` (OpenGL.zig:302). |
| 5 | Zig analysis | `src/renderer/Dmabuf.zig:55:20`, `:66:77` | `incompatible types: '*anyopaque' and 'comptime_int'`; `std.posix.system.close(fd)` | Same cause (fd comparison / close on HANDLE). |
| 6 | Link (lld-link) | `src/quirks_memset.zig:105` vs `libvcruntime.lib(memset.obj)` | `duplicate symbol: memset` | `main_c.zig:50` force-references the strong `memset` override; `GhosttyLib.zig:123,147` additionally links `libvcruntime`/`libucrt` on msvc, which also define `memset`. (Conflict only appears for the msvc DLL path.) |
| 7 | Link | `pkg/opengl/egl.zig`, `glad.zig` | undefined: `eglGetError`, `eglMakeCurrent`, `eglCreateContext`, `eglChooseConfig`, `eglInitialize`, `eglGetPlatformDisplay`, `eglBindAPI`, `eglQueryString`, `eglGetProcAddress`, `eglCreateImage`, `eglDestroyImage`, `eglDestroyContext`, `glad_eglExportDMABUFImageMESA`, `glad_eglExportDMABUFImageQueryMESA`, `gladLoadEGL`, `gladLoadGLContext`, `gladLoaderUnloadGLContext` (19 total) | `SharedDeps.zig:656-672`: glad (`vendor/glad/src/gl.c`, `glad_egl.c`) and `-legl` are only added when `step.kind != .lib` (and EGL only for `app_runtime == .gtk`). The `GhosttyLib` (`kind == .lib`) therefore has the OpenGL renderer but no loader, and EGL code is compiled in unconditionally on non-Apple. |
| 8 | Link | `src/termio/Exec.zig:126-127, 550` | undefined: `close`, `write` | `posix.system.close/write` on a pipe in `threadEnter`/`ThreadData.deinit`; Windows needs CloseHandle/WriteFile (`internal_os.pipe()` is already called there). |

Notes:
- Nothing past #8 is known; the link step stops there. Expect more once `ghostty-test` (which also compiles `src/main.zig`,
  `.use_llvm = true`, baseline CPU) is analysed; `main.zig:27,37` also imports `quirks_memset.zig` (same memset conflict likely).
- Error #6 shows the build already carries MSVC-specific workarounds (`GhosttyLib.zig:112-150`), so the intended direction
  upstream is msvc-ABI DLL, which depends on the installed MSVC Build Tools + SDK.
- Quirk: `src/build/Config.zig` still sets `emit_terminfo=true` on Windows and `font_backend=freetype_windows`; those paths
  compiled without errors in lib-vt only if used there, so they are untested by this recon.
